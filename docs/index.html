billing-core

A billing API that stays correct when clients retry.

A client times out and resends. A worker dies halfway. Someone gets charged twice. This is a small, tested answer to that problem: invoices, payments, credits and proration, with idempotency on every call that moves money.

This runs in your browser. It is a JavaScript model of the same rules as the Python API, not the live server. The requests here run one after another. The real concurrent test, with 20 threads on one database file, is tests/test_concurrency.py.

How it works

The idempotency check, the money movement and the stored response all live in one database transaction.

BEGIN IMMEDIATE            -- take the write lock first
SELECT ... WHERE scope = ? AND key = ?
  found, same body  -> replay stored response
  found, new body   -> 422 idempotency_key_reused
  not found         -> do the work, store the response
COMMIT

SQLite lets one writer through at a time, so two requests with the same key cannot both miss the lookup. The second waits, then replays.

Decisions worth a look

  1. Integer minor units. Proration uses (2n + d) // (2d), which is round half up with no float involved.
  2. Append-only ledger. The balance is derived on read, so it cannot drift from the history.
  3. Replay before business rules. A retry arriving after the invoice was settled gets the original 201, not a confusing 409.
  4. Same key, different body is an error. It is almost always a client bug, so it is not silently replayed.
  5. Errors say what to do next. Every error has code, message, retryable and next_step.
  6. Lock timeouts are retryable. A busy database returns 503 with an instruction to resend the same key.

I checked the concurrency test is not vacuous: with the key lookup disabled, it fails.

Limits

Not builtWhat a real system would do
Single writer (SQLite)Postgres with a unique constraint on (scope, key) and row locks
Keys never expireExpire after a window such as 24 hours
No payment gatewayAn "in progress" key state, since a gateway call cannot sit inside a transaction
No auth, refunds or taxAuth, a refund flow, an invoice state machine

This is a learning project, not production code.
